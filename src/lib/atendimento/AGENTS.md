# Attendance server and domain rules

- Anne's scope is booking only: `limparForaEscopoAna` (mirrored in `ana-claude/regras.ts` and `ana-rules.ts`) strips investigative questions, internal agenda rules and evaluation/referral promises; domestic violence keeps internal URGENT flag, a short acknowledgement that leads to real slots, safety question only on stated imminent risk, never a spontaneous 190. Why: Anne schedules, the Dra. evaluates.

- Intake defaults to automatic, preserving modes/pauses. Active `ana-prompt.txt` and `ana-restrictions.txt` supply identity with owner training; `ana-scheduling.ts` validates intent, offers and pending-slot consent. Why: no forced greeting or unsafe booking.
- Acquisition requests and contextual acceptance of a consultation invitation use shared `ana-rules.ts` policies in production and simulator; preserve selected-slot/name booking and the official ProJuris agenda. Why: prevent model-invented handoffs and repeated consent without bypassing legal or human controls.
- Ana inference uses `ana.functions.ts` with the uploaded `claudeComoSample` adapter; UltraMsg uses channel-validated orchestration, consent and released conversation-owned destinations. Telegram is retired and production restrictions apply before incoming processing and outgoing provider calls. Why: preserve operational safety and provider billing.
- Ana books, reschedules and cancels; process news uses the shared approval flow through server ports, while meaning, documents, contract, payment and legal advice stay team-only; `processo` intent still falls back to draft. Fictional slots are never stored as offers. Why: permit reviewed news without weakening legal or scheduling gates.
- Scheduling wallet is classified by `classificarAgenda` (intake-rules.ts): staff confirmation > active bond in the synced local base by principal phone > self-declaration > prior context > new-lead default. Active clients book Fridays only; new leads Monday–Thursday. Duplicate phone in the base is never self-classified — it goes to the team; cadastro-confirmed classification is persisted on the conversation. Why: exclusive days per client type without guessing bonds from conversation history.
- Slot offers use `parManhaTardeAna` (nearest morning + nearest afternoon); the initial deterministic greeting queries Calendar first and persists that offer. A choice without a name is held in `horarioPendente` and the full name is asked; the name then books that slot with revalidation, accepted while the slot is still in the future even if another message came in between, and a pending choice never transfers to the team. The client name is stripped before the ethics filter in `aplicarRegrasAna` ("Vitória" is a name, not "chance de vitória"). Choices are parsed after `normalizarEscolhaHorario` ("As9:30", "9 e meia"); a name arriving right after the name request recovers an unsaved choice from the previous client message, and Anne never claims a choice was noted unless it was persisted. Existing conversations, modes, pauses and human requests remain protected. Why: exact initial flow without invented availability or lost choices.
- Process news (`consulta_processo`, testing phase): `consulta-processo.ts` is the single flow for server and simulator. Identify by principal phone only; ask the subject without listing processes; one short notice; draft from server facts only (`ana-redacao-processo.txt`, validated, fallback template); local synchronized facts become the proposed text but, like provider drafts, every process notice waits for reviewer approval (AND-xxxx code + hash; ok/corrigir/não; only the configured reviewer or senior/admin); insistence while pending gets "em conferência" (including "??"), agenda keeps working; meaning, chances, values, documents, writes and third parties never consult. Why: confidentiality and no unreviewed legal information.
- Ana test battery: scenarios in `tools/simulador-ana/bateria/cenarios.ts` run on every suite (`src/test/ana-bateria-regressao.test.ts`, simulated classification) and on the "Bateria de testes da Ana" page with the real model and a 12-criteria evaluator. Add a scenario for every new rule or fixed bug. Why: change, automatic test, report, fix, retest without manual chats.
- Identified returns share `ana-retomada.ts` across production and simulator, append greeting and continuation through one verified send and never reset legal or scheduling context; identification also counts names found only in the persisted history (`nomeConhecido`), never the last-message date. Why: avoid duplicate sends and automatic onboarding on return.
- `historicoContato` sorts persisted messages chronologically by `dataHora` (stable), so out-of-order webhook deliveries never scramble Anne's context; the webhook persists the message before `processarAna` reads the fresh row. Why: continuity must come from the database, never from an open interface.
- Message deletion preserves original text and response replay markers, hides per user or tombstones only after verified provider acknowledgement; no calendar cancellation is implied. Why: keep audit evidence and avoid false deletion claims.
- Production recovery uses message JSON execution claims and authenticated managed scheduling; retry only pre-effect transient generation, never ambiguous sends or calendar changes. Human control revisions and explicit send reservations guard final UltraMsg calls and echo recognition. Why: durable browser-independent recovery without sending over staff.
- Ana health monitoring runs from a managed 5-minute schedule into `ana_monitoramento` with transition-only alerts in audit_log; Claude calls reserve a daily budget atomically via service-role database functions and per-conversation reply bursts are blocked. Why: 24/7 observability and spend/loop limits without browser timers.
- Day-of reminders run from a managed daily 08:00 São Paulo schedule (`lembrete-consulta.server.ts`), reserved before sending and never resent; cancellation consent is stored only after the send succeeds, so NÃO cancels through the existing guarded path. Why: no duplicate reminders or unauthorized cancellations.
- Daily 08:00 São Paulo report (`relatorio-diario.server.ts`, managed schedule) summarizes the previous day per client into priority / scheduling-only / in-progress, reserved once per day in `ana_monitoramento`. Why: one report, never duplicated.
- Incoming WhatsApp audio/voice (audio, ptt) is stored for staff but never starts intake or reaches Anne; `processarAna` returns early for audio. Why: the office handles voice messages manually.
